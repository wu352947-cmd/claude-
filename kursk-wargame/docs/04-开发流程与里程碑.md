# 04 · 开发流程与里程碑

> 时间按"一个人、业余时间（每周约 15–20 小时）"估算。全职或有队友可大幅缩短。
> 每个阶段都有**完成标准**——达不到就不进入下一阶段，这比赶进度重要。

## 总览

```
阶段0 研究与学习 ──► 阶段1 纸面原型(南线) ──► 阶段2 数据与地图 ──► 阶段3 数字垂直切片
   (2–3月)             (3–4月)                 (3–4月，与1部分并行)    (4–6月)
                                                                          │
阶段7 发行与社群 ◄── 阶段6 AI与打磨 ◄── 阶段5 全线战役 ◄── 阶段4 联机与校准
   (持续)              (6月+)            (6–9月)           (3–4月)
```

总计：到"朋友可以玩南线数字版"约 **12–15 个月**；到"全线战役 + AI"约 **2.5–3 年**。这对兵棋项目是正常节奏——很多商业兵棋从立项到出版也要数年。

## 阶段 0：研究与学习（2–3 个月）

**目标：** 建立史料与兵棋设计的基础，定下比例尺。

- 史料：通读 2 本综述（Glantz & House；Töppel 或 Frieser 主编的德国官方史第 8 卷相关章节），再精读南线专著（Zamulin、Lawrence、Nipe 任选）。做读书卡片，录入史料登记表。
- 兵棋：至少实际推完 2 款同题材/同尺度兵棋（见资源清单），记录"哪个机制让我感受到了历史"。
- 设计理论：读 Phil Sabin《Simulating War》前半部分——它专门讨论"如何让模拟具有历史有效性"，与你"历史可能性"的取向高度一致。
- 编程（如零基础）：TypeScript 基础 → 用 Canvas/PixiJS 画出一个六角格网并能点选格子（2–4 周）。

**完成标准：**
- [ ] 一页纸战役年表（7 月 4 日 – 8 月 23 日，按日）
- [ ] 南线 7 月 4 日双方战斗序列（到师/军级），每条有出处
- [ ] 比例尺决定书：每格多少公里、每回合多少时间、单位规模，以及理由
- [ ] 能在浏览器里显示一个可点击的六角格网

## 阶段 1：纸面原型——南线（3–4 个月）

**目标：** 用最低成本验证核心规则是否"好玩且像历史"。

1. 用粗糙地图（直接在打印的 1940 年代地图上画格子，或 QGIS 快速出图）+ 手写/打印算子。
2. 先只做 S1 普罗霍罗夫卡（9 回合），规则只包括：移动、控制区、战斗、撤退、发展阶段、可修复损失。
3. 推演→记录→改规则，循环至少 10 局。然后扩展到 S2 南线，加入工事、雷场、指挥点、空中。
4. 同时做 VASSAL 模块，让外地的朋友也能参与测试。

**测试记录模板（每局必填）：** 日期、想定、双方玩家、各回合关键决策、结果、与历史的差异、"哪条规则让人困惑"、"哪个时刻最像历史"。

**完成标准：**
- [ ] S2 南线可以由不熟悉的人照规则书完整推完
- [ ] 至少 3 名其他玩家测试过，且愿意再玩一次
- [ ] 结果分布大致合理：德军通常突入但无法达成战役突破；偶尔打得比历史好/差，且能说出原因

## 阶段 2：数据与地图（3–4 个月，可与阶段 1 后半并行）

**目标：** 建立"有出处的数据库"与正式地图。

- 按[史料复原方案](05-史料复原方案.md)录入南线全部单位、装备、增援表；建立争议登记表。
- 地图管线（技术架构 §4）跑通南线图：配准 → 矢量化 → 六角格提取 → 人工复核。
- 确定美术样式表，出第一张印刷级南线地图和一套算子。

**完成标准：**
- [ ] 南线数据通过 Zod 校验与出处检查（所有数值都有来源）
- [ ] 南线地图在桌面打印版与数字版中呈现一致
- [ ] 算子由脚本从数据自动生成

## 阶段 3：数字垂直切片（4–6 个月）

**目标：** 一个完整可玩的数字版 S1 + S2（热座）。

迭代顺序（每一步都可运行、可测试）：
1. 引擎骨架：状态、指令、事件、种子随机数、回放
2. 地图渲染：瓦片底图 + 格网 + 缩放平移 + 选择格子
3. 算子与堆叠显示、单位信息面板
4. 移动（寻路、移动范围预览）、控制区
5. 战斗（赔率预览 → 结算 → 撤退/追击）、损失与修理
6. 回合顺序、发展阶段、指挥点
7. 补给、工事/雷场、空中、天气、事件
8. 战争迷雾、热座切换
9. 胜利条件与战后报告（含"与历史对比"图表）

**完成标准：**
- [ ] 朋友在浏览器里能完整玩完 S1，不需要你在旁边解释
- [ ] 存档 = 指令列表；任意存档可 100% 回放复现
- [ ] 规则书中的每个示例都有对应的自动化测试

## 阶段 4：联机与历史校准（3–4 个月）

- PBEM 回合文件；可选 WebSocket 中继与服务器掷骰。
- 历史脚本 AI（A0）+ 无界面模拟器：S2 跑 ≥1,000 局，生成校准报告（见史料方案 §6）。
- 根据报告调整**公式参数**（不是单个单位），直到历史结果落在分布主体内。

**完成标准：**
- [ ] 两个人在不同城市能用 PBEM 或链接完成一局 S2
- [ ] 校准报告通过：关键指标的历史值落在模拟分布的 25%–75% 分位区间内（或有书面解释为何例外）

## 阶段 5：全线战役（6–9 个月）

- 依次加入北线（S3）、库图佐夫（S4）、鲁缅采夫（S5），每加一条战线都重复"数据 → 地图 → 校准"。
- 合成 S6 全线战役：跨战线调动、战略事件联动、苏军学习曲线。
- "假如"想定（W1–W5），每个都写一页设计说明与史料依据。

## 阶段 6：AI 与打磨（6 个月以上，持续）

- AI A1 → A2 → A3（技术架构 §6）
- 教程、规则百科（点击任何数字都能看到其来源与计算过程）
- 设计者笔记：每条主要规则"表现了什么历史、依据是什么"——这是专业兵棋的标志，也是推演价值的直接体现
- 本地化：中文为主，英文第二（国际兵棋社区主要用英文）

## 阶段 7：发行与社群（贯穿始终）

| 渠道 | 用途 |
|---|---|
| 小红书 / B 站 / 兵棋 QQ 群与论坛 | 开发日志、史料考据短文、测试招募（考据内容本身就很吸引军事爱好者）|
| BoardGameGeek / ConsimWorld | 国际兵棋社区，发布 VASSAL 模块与规则草案，收集反馈 |
| itch.io | 早期免费/付费测试版 |
| Steam | 正式数字版（Tauri 打包），先开"愿望单"页面积累关注 |
| 众筹（国内外平台） | 若要出实体版，需提前了解印刷、算子模切、物流成本 |

**开发日志建议主题：** "普罗霍罗夫卡到底损失了多少坦克？——我是怎么在游戏里处理这个争议的"、"为什么佩纳河在地图上这么重要"、"一张 1941 年苏军地形图如何变成六角格"。

## 给新手的学习路径（与阶段并行）

| 周 | 学什么 | 小练习 |
|---|---|---|
| 1–2 | TypeScript 基础（类型、函数、模块） | 写一个计算两格距离的函数 + 测试 |
| 3–4 | PixiJS 基础 | 画出六角格网、缩放平移、点击高亮 |
| 5–6 | 六角格算法（Red Blob Games） | 移动范围（Dijkstra）+ 路径（A*） |
| 7–8 | 状态管理与"指令/事件"模式 | 实现撤销/重做 |
| 9–10 | Zod 与数据驱动 | 从 JSON 加载 20 个单位并校验 |
| 11–12 | QGIS 基础 | 配准一张历史地图、画几条河流 |
| 之后 | Vitest、React、Node worker、Python GeoPandas | 按阶段需要学 |

**善用 AI 编程助手**：让它解释概念、写测试、审查代码；但规则设计与史料判断必须由你自己负责——这正是这个项目的价值所在。

## 风险与对策

| 风险 | 对策 |
|---|---|
| 范围失控（一开始就做全线） | 严格按 S1 → S2 → … 顺序；没通过完成标准不扩展 |
| 史料陷阱（采信回忆录或网络数字） | 史料分级 + 争议登记；关键数字至少两个独立 B 级以上来源 |
| 规则过于复杂 | 复杂度预算；数字版把"计算"藏到后台，把"决策"留给玩家 |
| 没人测试 | 从阶段 1 起就建测试群；VASSAL 让远程朋友参与 |
| 美术达不到预期 | 先定样式表，用真实地形形状 + 克制配色；找一位兼职美术做最终打磨 |
| 动力耗尽 | 每个阶段都有可分享的成果（地图、考据文章、可玩原型），持续获得反馈 |
| 版权问题 | 不复制商业兵棋的美术/规则文本；地图与数据只用可公开使用的来源，详见资源清单 §7 |
