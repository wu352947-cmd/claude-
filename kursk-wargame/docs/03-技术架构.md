# 03 · 技术架构

## 1. 技术选型（推荐方案）

| 层 | 选择 | 为什么 |
|---|---|---|
| 语言 | **TypeScript** | 类型系统帮新手少犯错；资料和 AI 编程助手支持最好；同一份代码可在浏览器和 Node 里跑 |
| 规则引擎 | **纯 TypeScript，无任何渲染依赖** | 能在 Node 里无界面跑上千局做历史校准；能写单元测试；以后换渲染引擎也不用重写规则 |
| 地图渲染 | **PixiJS v8**（WebGL/WebGPU） | 2D 性能好，9,000 格 + 数百算子 + 缩放平移毫无压力 |
| 界面 | **React** + 一个轻量状态库（Zustand） | 兵力表、战斗计算器、日志、OOB 浏览器这类信息密集界面用 DOM 写最省事 |
| 构建 | **Vite** | 零配置、热更新快 |
| 数据校验 | **Zod** | 所有 JSON 数据（单位、地图、想定、事件）加载时校验，录错数据立刻报错 |
| 测试 | **Vitest** | 规则引擎单元测试 + 历史回放回归测试 |
| 桌面版 | **Tauri**（后期） | 包体小；以后上 Steam |
| 联机 | 先 **PBEM 存档文件**，再 **WebSocket 中继**（可选 Colyseus） | 兵棋玩家习惯 PBEM；朋友之间异步对战最实用 |
| 地理处理 | **QGIS** + **Python（GeoPandas / Shapely / Rasterio）** | 史料地图配准、矢量化、自动生成六角格地形 |
| 美术 | **Inkscape / Affinity Designer**（矢量）、**Krita**（手绘纹理） | 印刷级地图与算子 |
| 军标 | **milsymbol**（JS 库，生成北约 APP-6 / MIL-STD-2525 兵种符号） | 算子符号标准化，不用手画 |
| 桌面原型 | **VASSAL**（免费）或 Tabletop Simulator | 线上推纸面原型，验证规则 |

> 备选：如果你更想用游戏引擎，**Godot 4**（免费、2D 很强、GDScript 易学）也完全可行。但**规则引擎必须与渲染分离**这一原则不变。本文以 Web 方案展开。

## 2. 总体分层

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层  PixiJS 地图渲染   React 界面   音效                   │
├──────────────────────────────────────────────────────────────┤
│ 交互层  输入 → 生成"指令"（Command）；预览（移动范围、战斗赔率）│
├──────────────────────────────────────────────────────────────┤
│ 会话层  本地热座 / PBEM 文件 / 网络中继 / AI 玩家（都只产生指令）│
├──────────────────────────────────────────────────────────────┤
│ 规则引擎（纯函数、确定性）                                     │
│   apply(state, command, rng) → { newState, events[] }         │
│   模块：回合顺序 移动 控制区 战斗 补给 指挥 空中 炮兵 工兵      │
│         情报 天气 事件 损失与修理 胜利                         │
├──────────────────────────────────────────────────────────────┤
│ 数据层  地图 六角格属性 OOB 单位 装备 CRT 事件 想定 史料出处    │
└──────────────────────────────────────────────────────────────┘
     ▲                                           ▲
     │                                           │
 工具链：地图编辑器 / OOB 编辑器 / 数据校验器 / 无界面模拟器 / 校准报告
```

### 2.1 核心原则：指令 + 事件溯源 + 确定性

- 玩家（或 AI、或网络对手）的每一个操作都是一条**指令**，例如 `{type: "Move", unit: "SS-LAH-PzRgt1", path: [...]}`。
- 规则引擎是一个纯函数：**同样的初始状态 + 同样的指令序列 + 同样的随机种子 = 同样的结果**。
- 一局游戏 = `想定 ID + 随机种子 + 指令列表`。这一个设计同时解决：
  - **撤销/重做**：回放到上一条指令
  - **存档**：只存指令列表，文件极小
  - **PBEM**：把指令列表发给对手
  - **联机同步**：双方只同步指令
  - **复盘/录像**：逐条回放
  - **历史校准**：用"历史命令脚本"自动生成指令，跑上千个种子
  - **找 bug**：玩家发来存档就能 100% 复现
- 随机数：使用可设种子的 PRNG（如 xoshiro128**），**禁止**在引擎中使用 `Math.random()`。
- 联机防作弊：骰子由服务器掷，或双方用"承诺—揭示"（commit-reveal）协议共同生成种子。

**实现（冲刺 3，2026-10-09）：**
- `engine/game.ts`：`GameState`（想定、主动方、回合、阶段、随机数状态、各单位格子与步数）；`Command`（Zod 校验）；`apply(ctx, state, command) → { state, events }`。随机数状态放在 `state.rng` 里，所以 rng 不单独传。
  非法指令抛 `CommandError`，不改变状态。现有指令：`Relocate`（临时移动，冲刺 4 换成正式移动）、`RollDie`（测试骰）、`EndPhase`。
- 回合顺序在 `data/rules/sequence.json`（按 02 §1 共 13 个阶段）。
- `engine/session.ts`：历史 = 指令列表 + 游标；撤销/重做只移动游标，状态由回放得到。
  存档 = 想定 + 种子 + 生效指令 + 最终状态指纹（FNV-1a）；读档时回放并核对指纹，不一致就报错（说明规则或数据改过）。
- 实际用的随机数算法是 mulberry32（`engine/rng.ts`），不是上文举例的 xoshiro128**。
- 界面：右下"对局"面板；浏览器里自动保存当前对局。

## 3. 数据模型

所有数据是**版本控制的文本文件**（JSON/CSV），游戏不硬编码任何历史数字。

### 3.1 目录结构

```
kursk/
  data/
    sources/            史料登记表 sources.csv、争议登记 disputes.csv
    equipment/          装备：panzer-iv-g.json, t-34-76-1943.json ...
    units/              单位：按集团军/方面军分文件
    oob/                编制树（谁隶属谁，何时变更）
    map/
      hexes.json        每格：地形、高程、村庄、工事等级、胜利点
      hexsides.json     每格边：河流等级、冲沟、铁路路堤、桥
      lines.json        道路、铁路
      names.json        地名（中/俄/德转写/英）
    crt/                战斗结果表、修正表
    events/             事件定义（DSL）
    scenarios/          想定：时间、范围、初始部署、增援表、胜利条件、历史基准
    weather/            历史逐日天气、气候概率表
  packages/
    engine/             规则引擎（纯 TS）
    schema/             Zod 数据模式（引擎与工具共用）
    client/             PixiJS + React 前端
    sim/                无界面模拟器、校准脚本（Node）
    ai/                 AI 玩家
    server/             联机中继（后期）
  tools/
    gis/                Python：地图配准后处理、六角格地形提取
    editor/             地图/OOB 编辑器（可以是 client 的一个模式）
  art/                  地图与算子的源文件（.svg / .afdesign / .kra）
  docs/
```

### 3.2 单位数据示例

见 [templates/unit.example.json](../templates/unit.example.json)。关键字段：

```jsonc
{
  "id": "DE.IISS.LSSAH.PzRgt1",
  "side": "DE",
  "names": { "zh": "…", "de": "…", "en": "…" },
  "parent": "DE.IISS.LSSAH",            // 编制树
  "type": "armor", "size": "regiment",
  "steps": 4,
  "ratings": { "attack": 0, "defense": 0, "movement": 0, "armorClass": "medium", "antiTank": "strong" },
  "equipment": [ { "ref": "pz-iv-g-h", "count": 0 }, { "ref": "tiger-i-e", "count": 0 } ],
  "asOf": "1943-07-04",
  "provenance": [
    { "field": "equipment", "source": "SRC-0012", "page": "…", "grade": "B", "note": "…" }
  ]
}
```

**`ratings` 不手填**，而是由 `equipment` + 人员 + 部队素质，通过一个**公开的换算公式**（`tools/derive-ratings`）计算出来。这样：①史料变了，数值自动跟着变；②玩家能看到算子数字是怎么来的；③校准时调的是公式参数，而不是一个个单位。

### 3.3 六角格坐标

- 使用 **轴向坐标（axial q,r）** 做计算，**偏移坐标（offset，如"2415"）** 做显示与桌面版编号。
- 寻路：Dijkstra 求移动范围、A* 求路径（按机动类型、地形、格边、控制区、天气计算成本）。
- 视线/观察（炮兵观察、高地）：六角格直线插值 + 高程。
- 参考 Red Blob Games 的六角格指南（见资源清单），照着它的公式写，别自己发明。

### 3.4 事件 DSL（数据驱动事件）

```jsonc
{
  "id": "EV-ZITADELLE-HALT",
  "when": { "date": ">=1943-07-13", "phase": "strategic" },
  "condition": "event('EV-SICILY') && germanArmorLossRatio('4PzA') > 0.3",
  "probability": "0.5 + 0.1 * turnsSince('EV-KUTUZOV')",
  "effects": [ { "type": "offerChoice", "side": "DE", "choices": ["HALT", "ROLAND", "CONTINUE"] } ],
  "sources": ["SRC-0003", "SRC-0007"]
}
```

条件与概率表达式用一个小型、安全的表达式解析器（不要用 `eval`）。

## 4. 地图生产管线（从史料到六角格）

```
① 收集史料地图           1940s 苏军总参 1:100k 地形图、德军翻印图、
                         美军 AMS 1:250k、战役态势图（档案/专著）
        ↓
② QGIS 配准              控制点：铁路交叉口、教堂、河流交汇；
                         统一投影：以 36°E 为中央经线的横轴墨卡托（或 UTM 37N）
        ↓
③ 矢量化（人工为主）      河流（分级）、冲沟、沼泽、林地、村庄、道路（硬/土）、
                         铁路、高地标高点；属性表记录来源图幅
        ↓
④ 高程                   Copernicus DEM GLO-30 / SRTM → 坡度、制高点
        ↓
⑤ 生成六角格网            QGIS 或 Python 生成 3 km 六角格，对齐地理坐标
        ↓
⑥ 自动提取（Python）      每格：主导地形（面积占比）、最高点、村庄；
                         每格边：与河流/冲沟/铁路路堤相交 → 格边特征
        ↓
⑦ 人工复核（地图编辑器）  对照态势图修正——"这条冲沟在历史上确实挡住了坦克吗？"
                         每处人工修改都记录理由与出处
        ↓
⑧ 导出                   hexes.json / hexsides.json / lines.json → 游戏
                         矢量图层 → 美术管线
```

**警惕现代地理：** 别尔哥罗德水库（1985 年建成）、战后新修的公路、消失的村庄、战后改道的河段。现代数据只用于高程，**地物以 1940 年代地图为准**。

## 5. 美术管线：做出"专业兵棋"的观感

你图中的两种风格：
- 图一（《Gulf Strike》VASSAL 版）：**以格为单位填色**，读图清楚但生硬；
- 图二（《Holland '44》）：**按真实地形形状绘制，六角格叠加其上**，美观且信息清楚——**推荐这种**。

### 5.1 地图

1. 以第 4 步导出的矢量图层为底稿（形状是真实的）。
2. 在 Inkscape/Affinity 中套用统一样式：配色、描边、纹理、标注字体。
3. **可读性规则**：任何一格的"游戏地形"必须一眼可辨——美术形状允许跨格，但每格的规则地形由数据决定；必要时在格中心加小符号。
4. 叠加六角格网、格号、地名、等高渲染（轻）。
5. 导出：
   - 桌面版：分图幅 PDF（印刷 CMYK、300 dpi，含出血）；
   - 数字版：多级瓦片（类似网络地图的金字塔切片），PixiJS 按缩放级别加载。

### 5.2 配色建议（与库尔斯克夏季景观相符）

| 元素 | 方向 |
|---|---|
| 开阔地/麦田草原 | 浅麦黄、浅灰绿，低饱和 |
| 林地 | 中暗绿，带手绘树冠纹理 |
| 冲沟 | 赭褐色细线 + 阴影 |
| 河流/沼泽谷地 | 蓝 + 蓝绿沼泽纹 |
| 村庄 | 灰褐色小块房屋，按实际轮廓 |
| 工事地带 | 地图上用淡红色细线标出历史防御地带（可开关） |

先定一张 **色板 + 字体 + 线宽** 的样式表，所有图层都从它取值；数字版与印刷版共用。

### 5.3 算子

- 尺寸：桌面版 5/8 英寸（约 16 mm）或 1/2 英寸；数字版矢量渲染。
- 正面：北约兵种符号（milsymbol 生成）+ 规模标记 + 番号 + 攻/防/移动 + 步数条。
- **师属色条**：同一师单位共享一条颜色，便于识别战斗群（《Holland '44》就是这样做的）。
- 阵营底色：德国陆军（Heer）原野灰系、武装党卫军偏深灰黑、苏军赭红/土褐系，近卫部队加标识。
- 背面：减员面（步数条变化）。
- 所有算子由**数据 + 模板脚本自动生成**（SVG 模板 → 批量导出），数据一改算子自动更新。

### 5.4 数字版的"兵棋质感"

- 视觉上保持桌面兵棋语言（算子、堆叠、格网），不要做成即时战略。
- 可选"算子 / 简洁军标"两种显示模式。
- 用叠加层显示：控制区、补给范围、移动范围、指挥范围、前线、历史前线对照（"历史上此时的战线"开关——推演价值的利器）。

## 6. AI 设计（后期）

作战级兵棋 AI 很难，分阶段：

| 阶段 | 方案 | 说明 |
|---|---|---|
| A0 | **历史脚本 AI** | 按史料设定的方向、时间表执行，作为"历史基准对手"，也是校准工具 |
| A1 | **规则型战术层** | 单格进攻/防守决策：赔率阈值、撤退条件、填补空隙 |
| A2 | **影响力图 + 作战层规划** | 计算双方力量分布与威胁，选出突破方向、预备队位置；集团军/军级任务分配（HTN 或效用 AI） |
| A3 | **蒙特卡洛评估** | 对关键决策（何时投入预备队）用无界面引擎前瞻模拟若干局 |

AI 只能通过**指令接口**行动，不能读取迷雾中的数据（否则就是作弊 AI）。

| 方式 | 实现 | 优先级 |

## 8. 测试策略

- **单元测试**：坐标、寻路、控制区、CRT 结算、补给追溯——每条规则至少一个测试，规则书上的每个例子都写成测试。
- **场景测试**：小地图 + 固定种子，断言结果（"德军装甲团在开阔地 3:1 进攻雷场中的 ПТОП，期望……"）。
- **历史回放回归测试**：用历史命令脚本跑 S2，每次改规则后自动比较关键指标的分布（见史料方案 §6）；偏离超阈值则 CI 失败。
- **数据校验**：所有数据加载时过 Zod 校验；另有一个"出处检查"——没有 `provenance` 的数值字段报警。
- **性能**：9,000 格 + 600 算子时，一次完整移动范围计算 < 16 ms。

## 9. 性能与规模提示

- 地图格属性用**扁平数组 + 索引**（typed array），不要用 9,000 个对象 + 字符串键。
- 渲染：地形是静态瓦片，算子用精灵批处理；叠加层只在变化时重绘。
- 模拟器：Node 中多进程（worker_threads）并行跑上千局。
