# CLAUDE.md — 库尔斯克 1943 兵棋项目规则

本文件是给 AI 编程助手的项目约定，每次开工前必读。项目所有者通过 vibe coding 开发：所有者负责设计、史料与验收，AI 负责实现。

## 先读这些

- `docs/01-设计总纲.md` … `docs/07-Vibe-Coding开发流程.md`
- `DEVLOG.md`（如存在）：最近的决定与进度
- 游戏代码在 `game/`

## 工作方式

- 用中文沟通；向所有者解释时不假设所有者懂编程。
- 一次只做一个功能。动手前先复述需求并给出简短计划；需求有歧义时先问。
- 不擅自扩大范围；顺手发现的问题列出来让所有者决定。
- 完成后汇报：改了什么、测试结果（实际运行输出）、所有者如何在预览中验收。
- 每完成一轮，在 `DEVLOG.md` 追加一行：日期、做了什么、做了哪些决定。

## 架构铁律

1. **规则引擎（`game/src/engine/`）是纯 TypeScript**：不得引用 PixiJS、DOM、浏览器 API；必须能在 Node 中运行。
2. **确定性**：引擎内禁止 `Math.random()`、`Date.now()`；只用传入的种子随机数。同一想定 + 种子 + 指令序列必须得到同一结果。
3. **指令/事件模式**：一切状态变化通过 `apply(state, command, rng) → { state, events }`；存档 = 想定 ID + 种子 + 指令列表。
4. **数据驱动**：历史数据、地图、CRT、修正值、移动消耗都放在 `game/data/` 的 JSON/CSV 中，并用 Zod 校验；代码中不硬编码规则数值。
5. **六角格**：计算用轴向坐标 (q, r)，显示用偏移坐标编号；算法参照 Red Blob Games。
6. 单文件尽量 < 400 行，按规则模块拆分（movement、zoc、combat、supply…）。

## 测试铁律

- 引擎的每条规则都要有 Vitest 测试；规则书中的每个例子写成测试。
- 修 bug 先写能复现的失败测试，再修。
- 提交前 `npm test` 与类型检查必须全部通过；不得为了通过而删除、跳过或放宽测试。

## 史料纪律（最重要）

- **禁止凭记忆编造或"估计"任何历史数字**（兵力、坦克数、损失、日期、位置）。
- 历史数值只能来自所有者提供的笔记/史料；每个数值带 `provenance`（来源 ID、页码、级别）。
- 尚未考据的数值用占位，标记 `"confidence": "placeholder"`；游戏界面中占位数据以灰色斜体显示。
- 整理所有者的笔记时，列出缺失、矛盾和你不确定的地方，而不是自行补齐。
- 史料冲突写入 `disputes.csv`，由所有者决定采用哪一说。
- 地物以 1940 年代地图为准，不用现代地图补地物。

## 界面与美术

- 保持桌面兵棋的视觉语言：六角格、算子、堆叠、北约兵种符号（milsymbol）、师属色条。
- 不使用纳粹/党卫军标志，用番号与兵种符号表示部队。
- 颜色、字体、线宽统一从样式表取值。
